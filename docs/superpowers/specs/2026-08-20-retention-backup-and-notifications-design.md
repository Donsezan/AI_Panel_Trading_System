# Retention, backup, and operator notifications

**Date:** 2026-08-20
**Status:** design approved, not yet implemented
**Pieces:** three, shipped in order — retention, backup, notifications

Three related changes to how the system keeps and surfaces its own record:

1. **Retention** — a three-stage lifecycle for the two heavy payloads. No event *row* is ever
   deleted, and every field a projector, report or cost total reads is kept forever.

   ```
   day 0 ──────────── day 30 ─────────────── day 90 ──────────────►
   full payload       archived to disk,      archive file deleted
   in the database    compacted from the db
                                             summaries, votes, costs,
                                             digests: kept forever
   ```

   Both windows are versioned configuration, not constants. This is DESIGN §6.9's stated policy —
   "full transcripts and full snapshots 90 days; summaries and snapshot hashes forever" — reached
   for the first time.
2. **Backup** — one consistent database copy per day, plus one before any schema migration.
3. **Notifications** — the alerts `ops/rules.py` already produces become visible on the dashboard,
   with a severity count in the header and a per-line dismissal that is recorded in the log.

---

## 1. Why

### 1.1 The designed policy was never built

DESIGN §6.9 specifies raw transcripts and `ContextSnapshot`s "stored compressed, referenced from
events, with a retention policy (e.g. full transcripts and full snapshots 90 days; summaries and
snapshot hashes forever)". [ADR 0003](../../adr/0003-event-log-as-source-of-truth.md) records the
status: **not yet implemented**. Neither half landed — payloads are uncompressed JSON stored
inline in `events.payload_json`, and nothing ever ages out. The one part that did land is the
per-cycle snapshot **digest**, which is precisely what keeps replay verifiable after compaction.

### 1.2 What that costs today

Measured on `data/sim.db` on 2026-08-19 (1 788 events spanning 2026-08-08 to 2026-08-19,
3.85 MB of payload JSON in a 5.7 MB database plus a 3.0 MB WAL):

| Event type | Rows | Payload | Share |
|---|---:|---:|---:|
| `SEAT_RESPONDED` | 866 | 2.33 MB | 61% |
| `SNAPSHOT_FROZEN` | 96 | 1.08 MB | 27% |
| the other 14 types | 826 | 0.44 MB | 12% |

Within those two, the compactable part is `response.raw_text` (1.32 MB, 58% of `SEAT_RESPONDED`)
and the `snapshot` body (essentially all of `SNAPSHOT_FROZEN`). **Compaction removes 2.37 MB of
3.85 MB — 62% of the log — without losing a single field any projector, report or cost total
reads.**

Volume is not flat. On 2026-08-18, 62 cycles wrote 76 `SEAT_RESPONDED` events (107 KB); on
2026-08-19, 68 cycles wrote 780 (2 156 KB). That is `SIM_PANEL` — three `varied-*` seats,
blind-then-debate, per instrument — replacing the single-seat `STUB_PANEL`. Per-cycle log cost
went from ~8 KB to ~47 KB, so a continuously supervised sim now writes roughly **23 MB/week**,
about 60% of it seat transcripts.

### 1.3 The two operational gaps

- **`docs/OPERATIONS.md` precondition 17** — "your tax and record-keeping requirements are known,
  and the event log's retention is set to match" — is currently unsatisfiable. There is no
  retention to set. It is a live-arming checklist item that cannot honestly be ticked.
- **`run_migrations` runs on every process start** (`persistence/database.py:72`) — every `serve`,
  every `run`, every CLI invocation. One bad autogenerated migration against `live.db` is the most
  likely way this system ever loses records that cannot be recreated, and there is no rollback
  point.

## 2. Decisions

Each was an explicit choice during design; the alternatives considered are recorded so a future
reader knows they were weighed rather than missed.

| # | Decision | Rejected alternative |
|---|---|---|
| D1 | Archive to file, **then** compact the payload — so nothing is unrecoverable *while the archive lives* | Compact in place (loses `raw_text` at day 30 rather than day 90); hard-delete rows (breaks rebuild, destroys the audit trail) |
| D1a | The archive file is **deleted** once its day passes the second window (default 90). Full transcripts and snapshot bodies are therefore retained for 90 days and no longer; summaries, votes, costs and digests are kept forever | Keeping archives indefinitely (the record grows without bound and DESIGN §6.9's policy is never actually met) |
| D2 | An in-process daily tick **and** a CLI command | CLI-only (a scheduled task nobody created backs up nothing); in-process only (cannot back up a stopped database) |
| D3 | Back up before a migration that will actually move the revision; a failed backup **blocks** the migration | Daily backup only (up to a day of cycles, orders and fills unrecoverable after a bad upgrade) |
| D4 | **Never** auto-delete a backup | Rotate at 14 or 30. Rejected by the operator; the accepted disk risk is mitigated by the free-space guard in §4.4 |
| D5 | Notifications are the **existing** `Alert` rules plus maintenance | A parallel notification entity (two answers to "what should the operator be told"); every event filtered by severity (~1 300/day trains dismissal-without-reading) |
| D6 | Dismissal is an audited act — an event in the log | A plain dismissals table (no audit line for "who cleared the mismatch notice"); session-only (re-floods on every restart) |
| D7 | Maintenance failures are HIGH; one LOW "ok" per day that **supersedes** yesterday's | Failures only (silence is ambiguous — a dead scheduler looks like a healthy one); a line per run (~90/month) |
| D8 | Header widget left of the `live-pill`, three counts high / medium / low in red/yellow/green | A single total (hides severity); a badge that appears only when non-empty (reflows the header during an incident) |
| D9 | Both windows live in a **versioned `maintenance` config document**, edited on the Parameters page | Environment variables (no record of what the policy was last month, for the setting that governs how long financial records are kept); two extra fields on `global_risk` (cheaper, but retention is not a risk limit) |

## 3. Piece 1 — retention

### 3.1 Where it lives

A new package, `tradebot/maintenance/`. **Not `ops/`**: CLAUDE.md's Phase 7 layering states that
everything in `ops/` and `validation/` reads, and only the alert dispatcher writes, and only its
own cursor. Compaction rewrites rows in the event log; placing it in `ops/` would silently break
the invariant that makes that layer trustworthy.

| Module | Job | Depends on |
|---|---|---|
| `archive.py` | write payloads to a day file, fsync, verify, return sha256 + counts | `persistence.schema` |
| `compaction.py` | the per-type payload rewrite, as a registry | `archive` |
| `backup.py` | consistent database copy, free-space guard | an engine or a path |
| `service.py` | order the passes, emit the events, report | the other three |

### 3.2 The compactor registry

```python
COMPACTORS: dict[EventType, Compactor] = {
    EventType.SEAT_RESPONDED: _drop_raw_text,     # response.raw_text
    EventType.SNAPSHOT_FROZEN: _drop_snapshot,    # snapshot; keeps snapshot_id + digest
}
```

Dispatch, not branching, per the repo conventions — and a type absent from the table is never
touched, so this can never grow to eat an event nobody reasoned about.

**Exactly what survives:**

- `SEAT_RESPONDED` keeps all 14 remaining fields of `response`: `vote` (action, conviction,
  size_hint, thesis, invalidation, key_risks), `call_id`, `cost_usd`, `model`, `provider_id`,
  `prompt_tokens`, `completion_tokens`, `latency_ms`, `seat_id`, `role`, `round_index`,
  `instrument_key`, `responded_at`, `abstain_reason`. Only the literal completion text goes.
- `SNAPSHOT_FROZEN` keeps `snapshot_id` and `digest`. The 17 KB body — candles, 39 indicators per
  instrument, positions, news — goes.

### 3.3 The invariant

**A projection rebuild after compaction must be byte-identical to one before it.** This is the
property the whole piece rests on, and it holds because:

- `SEAT_RESPONDED` has **no projector** (`PROJECTORS`, `projections.py:241`) and is **not** in
  `REPORT_TYPES` (`validation/evidence.py:46`). Nothing but the dashboard drill-down reads it.
- `_project_snapshot_frozen` (`projections.py:56`) reads exactly `payload["snapshot_id"]` and
  `payload["digest"]`, both retained.

It is asserted directly rather than reasoned about: rebuild, capture every projection table,
compact, rebuild, compare row for row.

### 3.4 The archive

One file per calendar day, per mode:

```
data/archive/<mode>/2026-07/2026-07-19.jsonl.gz
```

One JSON object per line: `seq`, `event_id`, `ts`, `type`, `payload` — with `payload` the original
**canonical** JSON, so a byte comparison against the stored row is meaningful.

**A day is archived only once it is entirely past `compact_after_days`**, which makes each file
immutable on creation — no partial rewrite, no torn file, and verification is a whole-file hash.
That is what keeps the horizon exact rather than rounding out to a month boundary.

Written to a `.tmp` sibling, fsynced, re-read and hashed, then atomically renamed. A file that
already exists and verifies is skipped.

### 3.5 Ordering, and what fails closed

```
for each day older than compact_after_days:
    write archive -> fsync -> re-read -> verify sha256 and row count
        (only on success)
    compact payloads, in chunks of ~200 rows through SingleWriter

then, last:
for each archive file whose day is older than archive_keep_days:
    delete it
```

**Nothing is compacted that is not already in a verified archive.** A failed or unverifiable
archive compacts nothing, records the reason, and raises a HIGH notification. `raw_text` from 31
days ago is never the last copy of itself.

Compaction is idempotent: a payload with no `raw_text` (or no `snapshot`) is already compacted and
is skipped, so a crash mid-pass costs nothing but a repeat.

**Deletion runs last, and only over the archive directory** — never over the database, and never
over a backup. It deletes whole day files by their name's date, so it needs no index and cannot be
confused by a partially written file (a `.tmp` is not a day file). A file that fails to delete is
reported and skipped; the next pass tries again.

One consequence worth stating rather than discovering: on a system that has not run maintenance for
months, the first pass will archive a day older than `archive_keep_days`, compact it, and then
delete that archive in the same run. That is the policy behaving correctly — a day past 90 is not
retained — but it means the first pass after a long gap can move data straight to gone. The daily
`MAINTENANCE_OK` line names how many day files were deleted, so it is never silent.

### 3.6 The compaction marker, and one lie it prevents

A compacted payload gains:

```json
"compacted": {"at": "2026-08-20T04:00:00Z", "archive": "2026-07/2026-07-19.jsonl.gz", "sha256": "..."}
```

`Event.payload` is `dict[str, Any]` (`core/events.py:78`) with no schema enforcement, so this
needs no model change.

It is also load-bearing for the UI. `templates/monitor/cycle.html:198-204` currently renders
*"No snapshot was frozen — the cycle was blocked before one was built"* whenever the body is
absent. For a compacted cycle that is **false** — a snapshot was frozen, deliberated on, and
archived. The drill-down must instead name the archive file, for both the snapshot and the seat
transcripts. `Queries.snapshot` already uses `.get("snapshot")` and returns `None`, so the change
is in the template plus a small accessor for the marker.

### 3.7 The windows are configuration, not constants

A third `ConfigKind`, `MAINTENANCE = "maintenance"`, singleton like `GLOBAL_RISK` — so
`ConfigKind.is_singleton` (`core/enums.py:181`) becomes a membership test rather than an identity
test, and the document lives under `SINGLETON_ID`.

```python
class MaintenancePolicy(DomainModel):
    compact_after_days: int = 30   # hot payloads archived and compacted after this
    archive_keep_days: int = 90    # archive files deleted after this
```

Four rules:

- **`archive_keep_days` must exceed `compact_after_days`**, enforced on the model. Inverted, a day
  would become eligible for deletion before it was ever archived, and each pass would rewrite and
  re-delete the same file forever.
- **`compact_after_days >= 1`.** Zero would compact the transcripts of cycles that are still
  running, emptying the drill-down of the thing an operator is currently reading.
- **A missing document means the model's defaults**, not a refusal. Maintenance and the daily
  backup share one tick, and refusing to back anything up because nobody published a policy would
  be fail-*useless*. The `MAINTENANCE_RAN` event records which windows were in force, defaults
  included, so the log always says what policy a pass ran under.
- **It is read fresh at each pass**, never captured at wiring — the same rule `app.enforced_policy`
  follows (ADR 0021). An edit takes effect at the next daily tick with no restart.

Editing is on the Parameters page beside the risk limits, through the existing forms → pydantic →
`configs.put()` path, so nothing restates a validation rule. Because it is a versioned document,
"who shortened retention to 7 days, and when" is answerable from `config history` — which is the
whole substance of OPERATIONS precondition 17.

**Deletion is the one act here that is irreversible**, so the shortening of `archive_keep_days` is
the edit to be careful about. It is versioned and attributable, but publishing 7 where 90 stood
will delete 83 days of transcripts on the next tick. The form states that next to the field.

### 3.8 Out of scope

`news_items` and `news_vectors` total 79 KB. Compacting them would be code with no benefit.
The 48-hour and 7-day lookbacks in `news/store.py` and `news/vectorstore.py` are **query** windows,
not retention, and are unchanged.

## 4. Piece 2 — backup

### 4.1 Mechanism

`VACUUM INTO`. The venv ships SQLite 3.45.1, well past the 3.27 minimum. One statement produces a
single consistent, defragmented `.db` file that already contains everything in the WAL — which a
plain file copy does not. It holds a read transaction only; on WAL that blocks no writer.

It runs on its own connection in a thread (`asyncio.to_thread`), never through `SingleWriter`, so
it cannot delay an order intent's append.

The output is an ordinary SQLite file: **restoring is copying it back over `data/<mode>.db`** with
the process stopped. No tool, no export format, nothing to remember at 03:00.

### 4.2 Naming and location

```
data/backups/<mode>/sim-20260820T040000Z.db                    daily
data/backups/<mode>/sim-pre-<revision>-20260820T040000Z.db     before a schema change
```

Default `data/backups/`, overridden by `TRADEBOT_BACKUP_DIR` or `--backup-dir`. Pointing it at a
second drive or a synced folder is recommended in OPERATIONS: a backup beside the database
survives a bad migration but not a dead disk.

### 4.3 Rotation

**None. Nothing the system creates is ever deleted by the system** (D4). Pruning is a human act.

### 4.4 The free-space guard

Because nothing rotates, the backup must not be what fills the volume. Before writing:

```
required = 1.2 x current database size + 200 MB headroom
```

If free space on the destination is below that, **no backup is written**: the run records the
reason and raises a HIGH notification. A full disk means the event log cannot accept an order
intent — technically a fail-closed refusal, operationally an outage.

### 4.5 The pre-migration hook

Inside `run_migrations` (`persistence/database.py:76`), before `command.upgrade`:

1. read the database's current revision (`MigrationContext.get_current_revision`) and compare it
   with the script directory's head;
2. **equal → return.** This is 99% of starts and costs one cheap query;
3. **different, and the engine is backed by a real file → take a backup first**, named for the
   revision being left (`base` when there is none);
4. **the backup fails → raise.** The migration does not run and the process does not start.
   Fail-closed on the one operation that can destroy irreplaceable records;
5. an in-memory engine (`path is None` — the entire test suite) is skipped by construction; a
   fresh database has nothing to copy and proceeds.

## 5. Piece 3 — notifications

### 5.1 The blocking defect it has to fix first

`AlertDispatcher.poll` and `.run` both return immediately when `enabled` is false, and `enabled`
is "any sink configured" (`ops/dispatcher.py:77-113`). On a machine with no webhook — the sim and
paper case — **the rules never evaluate at all**, so a bell fed by them would be permanently
empty.

`enabled` therefore comes to gate **delivery only**. The dispatcher always tails the log,
evaluates rules, and records what they produce; webhook and Telegram remain configured-only. One
evaluation, one persisted `RuleState`, no second opinion about what an alert is.

### 5.2 Two cursors, because recording and delivering fail differently

`_drain` currently advances one cursor **after** successful delivery, giving at-least-once
delivery (ADR 0019). Recording must not inherit that: a notification the operator can see must not
be withheld because a webhook is down, and a retry must not append a duplicate
`NOTIFICATION_RAISED` on every poll.

`alert_cursor` therefore gains `recorded_seq`:

- `recorded_seq` advances after the notification is appended — **exactly once per event**;
- `last_seq` keeps its present meaning and advances only after delivery.

There is no feedback loop: `_drain` reads `read_after(..., *ALERT_TYPES)`, and neither
`NOTIFICATION_RAISED` nor `ALERT_DISMISSED` is an alert type, so the dispatcher never reads its own
writes.

### 5.3 Severity

A `Severity` StrEnum (`high` / `medium` / `low`), exposed as a property on `AlertKind` — enum
behaviour lives on the enum. It replaces `is_urgent`, which only ever picked a sink's emoji.

| Severity | Kinds |
|---|---|
| HIGH | `KILL_SWITCH`, `BASKET_HALTED`, `RECON_MISMATCH`, `VALUATION_FROZEN`, `MAINTENANCE_FAILED` |
| MEDIUM | `PROVIDER_FAILURE`, `DATA_STALE` |
| LOW | `DAILY_SUMMARY`, `MAINTENANCE_OK` |

`VALUATION_FROZEN` is HIGH deliberately. It is not a breach and trips nothing, but it stops every
basket trading, and ADR 0027's stated reason for alerting on it is a soak sitting frozen overnight
with nobody told.

### 5.4 Maintenance as alert kinds

`service.py` appends exactly one event per pass — `MAINTENANCE_RAN`, carrying the outcome, what
ran, the resulting file size and any failure detail. It raises no alert itself. `MAINTENANCE_RAN`
joins `ALERT_TYPES` and gains one entry in the `RULES` table, which turns it into one of two kinds:

- `MAINTENANCE_FAILED` (HIGH) — backup failed, archive unverifiable, disk headroom short, or an
  unclassified error in the task.
- `MAINTENANCE_OK` (LOW) — one per day, carrying what ran and the resulting file size. **It
  supersedes the previous day's**: the projector marks any earlier undismissed `MAINTENANCE_OK`
  dismissed, with `dismissed_by = "system"`, so reassurance never stacks into thirty identical
  green lines. That supersession is derived from the log and therefore survives a rebuild
  unchanged, exactly like an operator's own dismissal.

A dedicated event type rather than an overloaded `RISK_EVENT`: maintenance is not a risk rule, and
`valuation_frozen` (`rules.py:218`) keeps sole ownership of that type. `ops/rules.py` stays one
function per event type — a new row in an existing table, not a new alerting path.

### 5.5 Storage

A new `notifications` projection table:

| Column | Notes |
|---|---|
| `alert_id` | PK, deterministic: `"{event_seq}:{kind}"` |
| `kind`, `severity`, `at`, `scope`, `title`, `body` | the rendered alert |
| `event_seq` | the event that produced it — the drill-down link |
| `dismissed_at`, `dismissed_by` | null until dismissed; `dismissed_by` is `dashboard` for an operator's click and `system` for a superseded `MAINTENANCE_OK` |

Deterministic identity is what makes the write idempotent. **On conflict the row is left
untouched, never overwritten** — a re-evaluation at 03:20 must not resurrect a notice dismissed at
03:12.

It is a true projection, folded from two new event types and listed in `PROJECTION_TABLES`:

- `NOTIFICATION_RAISED` — appended by the dispatcher when a rule produces an alert;
- `ALERT_DISMISSED` — appended by the dashboard, actor `dashboard`, as every dashboard action is.

So a rebuild reproduces the notification history **and** its dismissals exactly, and the log can
answer "who cleared the reconciliation-mismatch notice, and when".

`events.type` is a plain `String(48)` with no database-level enum, so new event types need no
migration. **The only schema change in this design is the `notifications` table plus the
`alert_cursor.recorded_seq` column.**

### 5.6 The header widget

Placed in `base.html` immediately after `<span class="spacer">` and **before** `#live-pill`
(`base.html:37-42`), so the group right of the menus reads: notifications → "live updates lost" →
"not trading" → Log out.

```
View  Parameters  Settings  Analytics          [ 1 | 0 | 3 ]   not trading   Log out
                                                 ^   ^   ^
                                              high  med  low
```

The counter **is** the button — the `<summary>` of a `<details>`, the same scripting-free idiom as
the Analytics menu. Colours are the variables already in `app.css`: `--danger` red, `--warn`
yellow, `--ok` green. No new colour enters the stylesheet.

Three rules on the counter:

- **Zeros stay visible and muted** (`1 | 0 | 3`, never `1 | 3`), with `tabular-nums` and a fixed
  minimum width. A widget that reflows on every socket tick moves the Log out link under the
  cursor of someone mid-incident.
- **Colour is never the only carrier.** Fixed high → medium → low order, plus a `title` /
  `aria-label` reading "1 high, 0 medium, 3 low" — so it survives a colourblind reader, a
  greyscale screenshot and a missing stylesheet.
- **All three zero → muted grey, not hidden.** "Nothing to tell you" and "the widget is broken"
  must not look identical.

### 5.7 Refreshing it without closing it

A pane normally refreshes with `hx-swap="outerHTML"` on its whole `<section>`
(`workspace/_pane.html`). Doing that to the `<details>` would **snap the dropdown shut while it is
being read**, up to once a second. The `<details>` element is therefore never the swap target.
Two inner regions carry their own `hx-get` against one route:

- the counts span — always refreshes;
- the list body — `hx-trigger="refresh[this.closest('details').open]"`, fetched only while open.

Both render through the same partial as first paint, preserving the Phase 10 rule of one rendering
path however the request arrived.

`Pane.NOTIFICATIONS` joins the `Pane` StrEnum (a wire contract), and `PANES_BY_EVENT` gains
**exactly two** new keys: `NOTIFICATION_RAISED` and `ALERT_DISMISSED`.

Deliberately not the five types the rules read. A kill-switch trip is seen by the socket tail
immediately, but the row it produces is written later, when the dispatcher next polls — so
refreshing the widget on `KILL_SWITCH_CHANGED` would repaint it before there is anything new to
show and then never repaint it again. Keying on the event the dispatcher itself appends is what
makes the bell correct rather than merely prompt.

### 5.8 Dismissal

The X is an ordinary POST form to `/control/notifications/{alert_id}/dismiss` — working with
scripting off, 303 back to the page it was posted from — enhanced with `hx-post`. It needs no
special refresh handling: appending `ALERT_DISMISSED` invalidates the pane through the socket, so
the widget re-renders itself and a second browser tab updates too.

The dropdown lists **every undismissed notification, newest first, never a time window**. An
unacknowledged alert that scrolls out of existence by itself is the one behaviour this must not
have. Dismissed rows stay in the table and remain readable under Analytics.

## 6. Scheduling and failure handling

### 6.1 A task of its own

`MaintenanceService.run()` is started alongside the supervisor by `run` and `serve`, exactly as
`AlertDispatcher.run` is. It is **not** a step in `Supervisor.serve`'s resync loop
(`supervisor.py:403`): a `VACUUM INTO` inline there would delay drift detection and the valuation
sweep by however long the copy takes.

Like the dispatcher's loop, it catches and logs any exception so a maintenance defect can never end
the loop or stop trading — and raises a HIGH notification so it is not silent.

### 6.2 Due-ness comes from the log

The `MAINTENANCE_RAN` event of §5.4 is also what answers "is a run due": due when
`start_of_day(now)` (`risk/state.py:176`) differs from the day of the newest one. One event, two
readers — no separate bookkeeping table, and a restart can therefore neither skip the day's backup
nor take a second, the rule every risk limit already follows.

Both windows come from the `maintenance` config document (§3.7), read fresh at each pass. The CLI
reads the same document, so the tick and a manual run can never disagree about what "old" means;
its `--older-than` / `--keep-days` flags are one-off overrides for a deliberate manual pass and are
recorded on the `MAINTENANCE_RAN` event as such.

It paces on the **injected `Clock`**, unlike the WebSocket tail's deliberate `asyncio.sleep`
departure: this is domain time, and a backtest stepping a month forward must not trigger thirty
backups.

### 6.3 Writer discipline

- `VACUUM INTO` — own connection, in a thread, read transaction only.
- Compaction — through `SingleWriter` in ~200-row chunks, yielding between them, so a cycle's
  `append` never queues behind a multi-second transaction.

### 6.4 Failure table

| Failure | Response |
|---|---|
| Disk headroom short | no backup written; HIGH notification; compaction skipped |
| Backup fails | HIGH notification; **compaction does not run** — compacting without a fresh backup is the one ordering that can lose data |
| Archive write or verification fails | nothing compacted for that day; HIGH notification |
| An archive file cannot be deleted | reported and skipped; the next pass retries; counted in the daily line |
| Pre-migration backup fails | `run_migrations` raises; the process does not start |
| Anything else in the task | logged; HIGH notification; the loop continues |

## 7. CLI

```powershell
tradebot maintenance backup  --mode sim [--backup-dir PATH]
tradebot maintenance compact --mode sim [--older-than N] [--keep-days N]
tradebot maintenance status  --mode sim
```

Both windows default to the `maintenance` config document; the flags are one-off overrides for a
deliberate manual pass, recorded as overrides on the event. `status` prints the windows in force
and where they came from, the last backup, the last compaction, the archive inventory and free
disk. A dashboard surface for `status` is deliberately deferred.

## 8. Testing

Rung 1 unless stated.

1. **The invariant** (`test_compaction.py`): rebuild → capture every projection table → compact →
   rebuild → identical, row for row. The single test that makes this safe.
2. Compaction: only registered types change; a second pass is a no-op; the marker is written;
   `digest`, `snapshot_id`, vote and cost survive; `raw_text` is gone.
3. Archive round trip: read back → payload byte-identical to the stored canonical JSON; a
   corrupted file fails verification and compacts nothing.
   - Deletion: only day files past `archive_keep_days` go; a `.tmp` is never matched; the database
     and the backup directory are never touched; an undeletable file is skipped and retried,
     not fatal.
   - The config document: `archive_keep_days <= compact_after_days` is refused by the model;
     `compact_after_days = 0` is refused; an absent document yields the defaults and the pass
     records which windows it ran under; an edit takes effect on the next pass without a restart.
4. Backup: the restored file opens and its `events` match; the disk guard refuses with an injected
   space probe; nothing is ever deleted.
5. Migration: same revision → no backup; differing → a backup named for the revision being left; a
   failing backup blocks the upgrade and leaves the schema untouched.
6. Notifications: a dispatcher with **no sinks** still records; `alert_id` is deterministic; a
   delivery retry does not resurrect a dismissed row; `recorded_seq` advances once per event while

## 10. Known risks

- **Backups accumulate without bound** (D4, the operator's explicit choice). Mitigated by the
  free-space guard, which refuses rather than fills; not eliminated. Pruning stays a human act.
- **Compaction is irreversible in the hot database.** Recovery means reading the archive, which is
  offline and deliberately not wired back into the dashboard. The invariant test plus the
  archive-then-verify ordering is what makes that acceptable.
- **Archive deletion is irreversible, full stop** (D1a). After `archive_keep_days` the literal
  model completion and the frozen snapshot body exist nowhere. This is DESIGN §6.9's intended
  policy and it is what makes precondition 17 answerable, but it is a genuine reduction in what
  can be reconstructed: after 90 days, "what exactly did the model say" is answerable only down to
  its vote, thesis, invalidation and key risks. If a jurisdiction ever requires the full text for
  longer, the window is a config edit — the mechanism does not need to change.
- **Shortening `archive_keep_days` acts immediately and destructively.** Publishing 7 where 90
  stood deletes 83 days of transcripts on the next tick. Versioned and attributable, but not
  undoable; the form warns beside the field.
- **`RuleState` streaks are re-evaluated on a delivery retry**, which can double-count a streak.
  This is pre-existing at-least-once behaviour, unchanged here, and noted so it is not read as new.
